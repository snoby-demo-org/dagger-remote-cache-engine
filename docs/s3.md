# Connecting the coordinator and engines to S3

This guide documents the **current prototype**, not every feature proposed in the [historical designs](history/README.md). See [current architecture](design.md), [engine setup](engines.md), and [executed verification](../VERIFICATION.md).

## Topology and ownership

```text
CLI/runner -- session telemetry --> coordinator -- SQLite checkpoint --> persistent disk
engines    -- WebSocket control --> coordinator -- signed HEAD/GET/LIST/DELETE/PUT-bucket --> S3
engines    -- signed PUT and GET/Range-GET ---------------------------------------------> S3
coordinator -- full streamed GET + SHA256 verification -------------------------------> S3
```

Use **one coordinator replica and one persistent SQLite directory per trusted pool**. S3 stores blob bytes, not the coordinator's SQLite database. Sharing a bucket does not make multiple graph writers safe. Engines retain independent local caches; they do not need a common `/var/lib/dagger` mount.

## Configuration

Start from [coordinator.env.example](../examples/coordinator.env.example). Its required secret fields are deliberately empty so an unedited example fails validation. Load values through your own secret manager; do not commit a filled file.

| Setting | Meaning |
|---|---|
| `S3_ENDPOINT` | HTTP(S) origin used by the coordinator for its signed internal S3 requests |
| `S3_PUBLIC_ENDPOINT` | HTTP(S) origin placed into engine-facing signed URLs; defaults to `S3_ENDPOINT` |
| `S3_BUCKET` | Dedicated bucket name; there is no separate arbitrary-prefix setting |
| `S3_REGION` | Signature region; default `us-east-1` |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Static S3 API credentials available **only to the coordinator** |
| `DCACHE_POOL` | Safe pool name; default `shared` |
| `DCACHE_URL_TTL` | Signed URL lifetime; default `15m`, CLI requires a positive duration, maximum `168h` |
| `DCACHE_DB` | Persistent local database file; example container path `/state/cache.db` |
| `DCACHE_TOKEN` | Shared engine/telemetry authentication token; at least 16 characters |
| `DCACHE_HMAC_SECRET` | Server-only renewal-signing secret; at least 32 bytes; preserve across restarts |

Generate a pool token once, for example `dck-` followed by `openssl rand -hex 32`, and a separate HMAC secret with `openssl rand -hex 32`. Save both values securely rather than generating replacements on each startup. Changing them invalidates existing authentication/renewal capabilities. Do not give S3 credentials or the HMAC secret to engines or runner pods.

The current backend builds **path-style** URLs:

```text
https://<s3-origin>/<bucket>/pools/<pool>/blobs/sha256/<64-lowercase-hex-digits>
```

Endpoints must be origins such as `http://objectstore:9000` or `https://storage.example.test`, not URLs with `/bucket`, `/prefix`, embedded credentials, or query parameters. The storage implementation rejects a non-root endpoint path. Set the bucket separately. Use simple bucket names supported by your provider and pool names matching `[A-Za-z0-9][A-Za-z0-9._-]*`.

## Bucket initialization and permissions

The CLI **always calls `EnsureBucket` before opening its listener**, including when a bucket already exists. The implementation sends `PUT /<bucket>` and accepts HTTP 200/201 or the explicit `BucketAlreadyOwnedByYou` conflict response. Access denied is not silently ignored. There is no `--skip-create-bucket` flag.

**AWS production caution:** AWS documents that repeating `CreateBucket` against an already-owned bucket in `us-east-1` can reset its ACLs. This prototype's unconditional startup call has not been hardened for that behavior. Do not point it at an existing production AWS bucket or broaden production permissions merely to make startup succeed; bucket initialization needs provider-specific validation first.

Provision credentials for the actual operations below, using your S3 provider's policy system. This is an operation checklist, not a claim that a particular AWS IAM policy was tested:

| Resource | API operation | Used for |
|---|---|---|
| Bucket | Create/initialize bucket (`PUT /bucket`) | Mandatory startup check |
| Bucket | ListObjectsV2, restricted to this pool prefix where supported | Listing/sweeper helper |
| Pool objects | PutObject | Engine uploads using presigned URLs |
| Pool objects | HeadObject and GetObject, including byte ranges | Existence, exact-size checks, verification, downloads and renewal |
| Pool objects | DeleteObject | Best-effort deletion helper and destructive test scenarios |

For AWS-style policy planning the corresponding action names are `s3:CreateBucket`, `s3:ListBucket`, `s3:PutObject`, `s3:GetObject` (also covers HEAD), and `s3:DeleteObject`; validate provider-specific policy and bucket-creation behavior independently. **Real AWS S3 and non-default-region bucket creation have not been certified.** The current empty-body bucket-creation request does not send a region `LocationConstraint`.

Only static access/secret credentials are implemented. There is **no session-token/STS option, role credential chain, SDK default credential discovery, KMS-header configuration, virtual-hosted-style selector, or multipart-upload API** in this prototype. Setting ordinary `AWS_*` credential variables alone does not configure it. Do not assume AWS role-based deployments work unchanged.

## Endpoint reachability, signatures, and TLS

- The coordinator must resolve/reach `S3_ENDPOINT`; every engine must resolve/reach `S3_PUBLIC_ENDPOINT`. These can differ, but must address the **same underlying bucket and bytes**.
- All pool members need direct S3 connectivity. Forwarding only the coordinator port does not proxy blob traffic.
- The signed method, host and path must arrive unchanged. A proxy that rewrites the signed host, bucket path, encoding or query can produce `SignatureDoesNotMatch`.
- Support full PUT/GET, HEAD, and HTTP Range requests. The verifier performs a full bounded readback; it is not a metadata-only check.
- Keep system clocks synchronized. Signed URLs expire and should be treated as temporary bearer capabilities; do not publish them in logs or support tickets.
- Plain HTTP is appropriate only for isolated trusted fixtures. Use trusted HTTPS endpoints outside that setting; install any required CA trust in both coordinator and engine environments. The service has no built-in TLS listener, and this backend has no insecure-skip-verify switch. Terminate coordinator TLS at a correctly configured private proxy.
- There is no coordinator setting that guarantees object retention in your provider. Avoid lifecycle expiration that removes still-referenced cache objects. Cache loss may safely require recomputation, but will reduce reuse.

## Starting and checking

On Linux, build with `make build`. Configure the variables above and run `./bin/dcache`. For a container, mount the tested Linux binary and a writable persistent directory, as shown in [engine setup](engines.md).

Read-only coordinator checks:

```sh
curl --fail http://dcache:8080/healthz
curl --fail -H "Authorization: Bearer ${DCACHE_TOKEN}" http://dcache:8080/debug/state
curl --fail http://dcache:8080/metrics
```

`/healthz` and `/metrics` are **unauthenticated**; only the debug-state example above requires the pool token. Keep metrics on your private network or enforce protection at a proxy if needed. Liveness is not a guarantee that every object remains readable. Check coordinator logs, peer registration and publication state, then prove reuse using the [real engine tests](testing.md). Keep debug output and operational telemetry private.

The standalone S3 integration test and functional tests create/write/delete fixture data. Run them **only against disposable resources**; see [testing](testing.md) for exact commands and credentials expectations. Do not point them at an existing production bucket.

## Troubleshooting and limits

| Symptom | Check |
|---|---|
| Startup `ensure bucket` failure | Endpoint, static credentials, bucket ownership, create permission and provider-specific region behavior |
| Engines connect but upload/import fails | Engine-visible S3 DNS/routes, TLS trust, proxy rewriting, range support and expiry |
| Signature mismatch | Region, exact host/path/query preservation, clock skew, and whether an unsupported temporary credential was used |
| Published metadata but later cache miss | Missing/corrupt object, expired capability, pruning/GC, or a different recipe identity |
| Cache state lost after coordinator replacement | Persistent `DCACHE_DB` directory and stable token/HMAC secret; S3 alone cannot restore graph state |

RustFS passed the actual authenticated upload/range/hash/corruption/delete tests. That is **not** certification of every S3-compatible provider. Publication checks exact size and SHA256 before advertising parts; downloads bypass the coordinator. A persistently corrupt preexisting object can require removal before a later export repairs it. Storage List/Delete primitives exist, but there is **no implemented periodic S3 sweeper or HTTP sweep endpoint** in this CLI. Orphaned objects may accumulate. Do not manually delete live objects as routine maintenance.
