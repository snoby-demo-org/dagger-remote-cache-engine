# Concurrent object-storage build caches: capability and prior art

**Research cutoff:** November 5, 2026, approximately 23:15 EST (November 6 UTC). Deployment context supplied by the caller: k3s, Helm Dagger engines v0.21.9, ARC runners, and possible node removal with roughly 30 seconds' notice. This was internet/source research, not a load test or a change to the deployment. Live GitHub API discovery confirmed **v0.21.11** as the latest stable Dagger release (published October 21, 2026) and **v1.0.0-beta.25** as the highest numbered 1.0 beta tag. [Stable release](https://github.com/dagger/dagger/releases/tag/v0.21.11); [beta tag discovery API](https://api.github.com/repos/dagger/dagger/git/matching-refs/tags/v1.0.0-beta.).

## Bottom line

- **S3 supports many independent writers; a single mutable cache index usually does not merge their work.** Separate immutable/content-addressed blobs from action/task-result metadata; publish metadata only after the referenced bytes are durable. This is the important distinction between object-store atomicity and application-level cache correctness. [S3 consistency and single-key atomicity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel); [REAPI ActionCache/CAS](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto); [OCI upload order and concurrency](https://github.com/opencontainers/distribution-spec/blob/main/spec.md).
- **Dagger v0.21.x has no working replacement for the old BuildKit S3 cache-export environment variable.** A maintainer explicitly says it was dropped when the BuildKit backend was replaced, not that S3 itself stopped supporting concurrency. The 1.0-beta line contains a different, open engine-side remote-cache protocol, but it is not a direct S3 backend or a packaged self-hosted service. [Dagger #13405](https://github.com/dagger/dagger/issues/13405); [remote-cache PR #14388](https://github.com/dagger/dagger/pull/14388).
- **For an immediate self-hosted deployment, retain engines on persistent infrastructure and make runners ephemeral, or add language/task caches independently of Dagger's engine cache.** Dagger's current self-hosting guide explicitly recommends persistent engines/disks and warns against ephemeral engine pools; sccache, Bazel/bazel-remote, Turbo, and Nx provide useful independent remote-cache paths, not drop-in Dagger engine-cache replacements. [Dagger self-hosting](https://docs.dagger.io/self-hosting/index); [sccache S3](https://github.com/mozilla/sccache/blob/main/docs/S3.md); [Bazel caching](https://bazel.build/remote/caching); [Turbo caching](https://turborepo.com/docs/core-concepts/remote-caching); [Nx caching](https://nx.dev/docs/guides/tasks--caching/self-hosted-caching).
- **A 30-second shutdown hook is not a durability mechanism.** Design to retain completed remote commits during normal operation and lose only in-flight/unpublished work. Dagger beta's remote-cache client explicitly cancels uploads when its context is canceled; neither its source nor the docs establish a guarantee that every completed operation is remotely durable before the operation returns. [Dagger remote-cache client lifecycle](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/remotecache.go); [protocol](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/protocol/protocol.go).

## 1. Dagger 1.0-beta: what is actually available

### Documentation versus source

The default `docs.dagger.io` self-hosting and `engine.json` pages identify themselves as **1.0-beta**. They document persistent engines and engine configuration, but I did **not** find a prose remote-cache setup guide or an official self-hosted cache-server deployment guide. Importantly, the **machine-readable schema hosted on docs.dagger.io does document `remoteCache.url`**, its `DAGGER_CLOUD_TOKEN` prerequisite, and the environment-variable override. Therefore “not documented anywhere” would be inaccurate; the available operational detail is principally the schema and source/PR, not a complete guide. [Self-hosting](https://docs.dagger.io/self-hosting/index); [engine.json reference](https://docs.dagger.io/reference/config-files/engine-json); [published schema](https://docs.dagger.io/reference/engine.schema.json); [version-pinned schema](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/docs/static/reference/engine.schema.json).

Verified engine configuration shape (the URL below is a placeholder, **not** an existing public endpoint):

```json
{
  "remoteCache": {
    "url": "https://cache.example.internal"
  }
}
```

`_EXPERIMENTAL_DAGGER_REMOTE_CACHE_URL` overrides that URL. The **engine process** also requires `DAGGER_CLOUD_TOKEN` to be nonempty and not the literal `oidc`; a token alone does not enable remote caching. These exact checks are in beta.25's `remoteCacheSettings`. Helm accepts JSON via `engine.configJson`; engine environment variables must be injected into the engine pod, not merely assumed to be present in an unrelated runner. [Configuration gate](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/cmd/engine/remotecache.go); [Helm/config documentation](https://docs.dagger.io/reference/config-files/engine-json).

The client appends `/v1/engine` to the configured service URL and opens a WebSocket. Authentication is HTTP Basic with the configured token as the username and an empty password. **Source inference:** the local gate does not validate that this is a real Dagger Cloud-issued token, so a custom service can implement its own acceptance policy; that is not a vendor-supported self-hosted configuration. Do not send a real Cloud credential to an untrusted custom URL. [Dial/auth implementation](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/remotecache.go); [endpoint/protocol constants](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/protocol/protocol.go).

### Protocol and service boundary

The remote-cache engine-side PR merged September 29, 2026. It describes the reference service as running in **Dagger Cloud**, with the service implementation in `dagger/dagger.io#5379`; that is not a public server implementation in `dagger/dagger`. The open beta code exchanges `hello/welcome`, `export/exported`, `upload/uploaded`, `merge/merged`, `offer/offered`, and `renew/renewed`. The service asks for selected cached values/parts, supplies presigned PUT URLs for missing blobs, and distributes result metadata and download addresses to other engines; layer downloads are lazy. This is a control plane plus a blob plane, **not** a bucket URL substituting for the control plane. [PR #14388](https://github.com/dagger/dagger/pull/14388); [open protocol](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/protocol/protocol.go).

**Additional implementation requirement easily missed:** enabling remote cache automatically enables engine cache events. Those events use a separate telemetry exporter, directed at `DAGGER_CLOUD_URL`, with `DAGGER_CLOUD_TOKEN`; setting only `_EXPERIMENTAL_DAGGER_REMOTE_CACHE_URL` does not redirect this event stream to the WebSocket server. A replacement service must account for cache discovery/event ingestion as well as WebSocket requests and blob storage. A dummy token plus a `/v1/engine` handler is therefore **not established as a complete working solution**. Event-loss/reconciliation and exact custom telemetry/auth setup were not integration-tested here. [Enabling events](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/cmd/engine/remotecache.go); [event exporter and separate destination](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/cmd/engine/telemetry.go); [PR architecture](https://github.com/dagger/dagger/pull/14388).

The protocol and dagql primitives are public implementation material; a deployable, supported self-hosted server image/chart was **not verified**. The docs instead recommend persistent self-hosted engines. This is a bounded search result, not proof that no unpublished/commercial implementation exists. [Open engine directory](https://github.com/dagger/dagger/tree/v1.0.0-beta.25/engine/remotecache); [self-hosting architecture](https://docs.dagger.io/self-hosting/index); [reported custom implementation](https://github.com/dagger/dagger/issues/14657).

## 4. BuildKit `type=s3`: capabilities and concurrency model

Upstream BuildKit documents an **experimental S3 cache exporter/importer**. The current Docker S3-backend page labels availability **Experimental**, explicitly says the default `docker` driver is unsupported, and instructs users to create a builder with another driver. Do not repeat an older “unreleased” label or assume every builder image supports it. The BuildKit daemon needs the AWS credentials/configuration. It supports an alternate endpoint and path-style addressing for compatible stores. Example direct BuildKit syntax: [BuildKit README](https://github.com/moby/buildkit#s3-cache-experimental); [Docker S3 backend](https://docs.docker.com/build/cache/backends/s3/).

```sh
buildctl build ... \
  --import-cache type=s3,region=us-east-1,bucket=ci-cache,name=main \
  --export-cache type=s3,region=us-east-1,bucket=ci-cache,name=job-unique,mode=max
```

### Data layout and race behavior

- Blobs are keyed by digest under `blobs/`; a named manifest is under `manifests/<name>` (both prefixes configurable). The S3 manifest is serialized BuildKit **CacheConfig JSON**, with `layers` and `records`, layer parent indices, blob digests, DiffIDs, media types, sizes, and result/input links. It is **not itself an OCI image index**. The same cache-config type also has the media-type constant `application/vnd.buildkit.cacheconfig.v0`; registry exporters wrap cache data differently. [S3 implementation](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/s3.go); [format types](https://github.com/moby/buildkit/blob/master/cache/remotecache/v1/types/spec.go).
- Export finalization uploads/checks the selected layers, waits for them, marshals the cache config, then writes each named manifest. The implementation uses HEAD to check blobs and an unconditional mutable-object upload for manifests; it does not fetch/merge the old named manifest or use a compare-and-swap when writing it. **Source inference:** two exporters sharing one manifest name compete, and a winning manifest need not contain the other build's unique cache records. The digest blobs can both survive while the overwritten metadata makes some unreachable from that name. [Finalize/saveMutableAt implementation](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/s3.go); [Docker warning about overwriting cache locations](https://docs.docker.com/build/cache/backends/).
- This metadata lost-update problem is **not automatically byte-level corruption**: S3 single-key replacement is atomic. Identical digest-key blob writes should carry identical content; if they do not, hash validation/cache key correctness is already broken. Separately, expiration/GC can remove referenced blobs, and client implementation bugs can mishandle otherwise correct objects. [S3 atomicity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel); [BuildKit digest layout and upload code](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/s3.go).
- Use separate write names for branch/platform/build or immutable per-job manifests, import multiple known manifests, and allow only a designated publisher to update a shared `main` alias. BuildKit explicitly supports multiple exporter names separated by semicolons and multiple import-cache flags. **Design tradeoff:** more immutable manifests require discovery/retention management; the stock S3 importer reads a supplied name, not every manifest in the bucket, and arbitrary writers are not unioned automatically. [BuildKit S3 options](https://github.com/moby/buildkit#s3-cache-experimental); [S3 importer](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/s3.go).
- Existing blobs are touched by server-side copy after `touch_refresh` (default 24h), and manifests are rewritten on export, enabling age-based lifecycle cleanup. This introduces COPY/HEAD costs and does not make S3 lifecycle a reference-aware GC. **Design inference:** retention must exceed expected manifest/read lifetime, or readers must tolerate missing blobs as cache misses. [BuildKit README](https://github.com/moby/buildkit#s3-cache-experimental); [touch implementation](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/s3.go); [S3 lifecycle expiration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html).

### Verified implementation failures, distinguished from multi-node contention

BuildKit **#6674** reports a reproducible concurrent `ReadAt` race/panic while reading an S3-backed layer and re-exporting through the AWS multipart uploader; PR **#6675** merged April 10, 2026, adding a mutex. This is intra-daemon concurrency, not proof of S3 corrupting objects when separate CI nodes write them. Pin/test an actual BuildKit release containing the fix rather than assuming a random installed version is safe. [Bug](https://github.com/moby/buildkit/issues/6674); [merged fix](https://github.com/moby/buildkit/pull/6675).

PR **#7123** describes additional short-read/offset problems, but the authenticated API says it is **closed without merge**. Current `master`'s reader already differs in the short-read condition and offset handling from that PR's reported buggy code. I did not establish the precise release containing every relevant fix and do not treat that unmerged PR as proof of a current-master defect. [PR #7123](https://github.com/moby/buildkit/pull/7123); [current reader](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/readerat.go).

## 5. Prior-art patterns worth copying

### Bazel / REAPI: distinct ActionCache and CAS

Bazel separates action-result lookup (keyed by the action digest) from content-addressed output bytes; HTTP paths are `/ac/` and `/cas/`. REAPI formalizes ActionCache and ContentAddressableStorage, including missing-blob checks and upload identities that prevent concurrent upload-session collisions. ActionCache is **not** identical to immutable output CAS: it maps an action to an execution result and may be updated. GetActionResult implementations should ensure referenced blobs are available and retained for a useful period. [Bazel documentation](https://bazel.build/remote/caching); [REAPI services and concurrency rules](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto).

`buchgr/bazel-remote` is an actual public self-hosted server with HTTP/gRPC interfaces and S3/MinIO proxy storage. **Critical teardown caveat:** its proxy has a bounded upload queue, skips uploads when full, and processes them with background upload workers. Therefore placing the proxy itself on a disposable node does not imply remote durability at the moment a client receives local cache success. Keep that gateway persistent or verify/change its acknowledgement semantics for the required durability contract. This conclusion is an inference from the documented queue, not a fault-injection result. [README/configuration, `max_queued_uploads` and `num_uploaders`](https://github.com/buchgr/bazel-remote/blob/master/README.md).

### sccache S3: per-compilation entries, no global build manifest

sccache directly supports S3-compatible endpoints, bucket/prefix scoping, standard credentials, and read-only access. Its remote storage implementation serializes a cache entry and writes the normalized compilation cache key through OpenDAL; it is not one shared mutable index containing every build. **Source inference:** independent keys avoid the whole-index overwrite conflict, while two writers to the same compilation key can still overwrite that entry; the inspected sccache layer does not request first-writer-wins conditional writes. Correctness still depends on complete compiler/input/environment keys and trusted writers. It is a compiler cache, not a Dagger operation-cache adapter. [S3 configuration](https://github.com/mozilla/sccache/blob/main/docs/S3.md); [remote storage `put_raw`](https://github.com/mozilla/sccache/blob/main/src/cache/cache.rs); [S3 operator construction](https://github.com/mozilla/sccache/blob/main/src/cache/s3.rs).

### Turborepo: task archives and optional signatures

Turbo supports a documented remote-cache HTTP API and lists community servers. It can sign artifacts using **HMAC-SHA256** and treat a failed authenticity/integrity check as a cache miss. This protects against untrusted/wrong artifact bytes better than assuming an input hash makes storage trustworthy; logs are artifacts too, so secrets printed to logs must not enter a broadly readable cache. [Turbo remote-cache documentation](https://turborepo.com/docs/core-concepts/remote-caching).

`ducktors/turborepo-remote-cache` is public and supports S3/MinIO. Its S3 backend streams into the AWS upload manager, awaits upload completion, stores artifact metadata with the body, and attempts to abort unfinished multipart uploads when streams fail. This is useful write-path prior art; it does not by itself establish no-overwrite semantics, universal fail-open behavior, or tested Dagger integration. [Storage provider documentation](https://github.com/ducktors/turborepo-remote-cache/blob/main/docs/supported-storage-providers.md); [S3 streaming/abort implementation](https://github.com/ducktors/turborepo-remote-cache/blob/main/src/plugins/remote-cache/storage/s3.ts).

### Nx: explicit non-overwrite API

Nx publishes a self-hosted remote-cache OpenAPI specification: bearer-authenticated GET/PUT `/v1/cache/{hash}`, tar archives, 404 for misses, and **409 when an existing record cannot be overridden**. This is clear first-writer-wins API-level prior art, unlike a shared mutable branch archive silently overwriting another writer. A conforming object-store implementation should enforce that atomically, not with a racy HEAD-then-PUT sequence. Configuration is `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` plus `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN`. [Nx official specification](https://nx.dev/docs/guides/tasks--caching/self-hosted-caching); [S3 conditional writes for implementation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

### GitHub Actions cache: reserve, upload, finalize; lease claims require care

The public Actions toolkit implements a reservation/create phase, upload to a signed URL, and a finalize/commit phase. V2 uses `CreateCacheEntry`, direct Azure SDK archive upload, then `FinalizeCacheEntryUpload`; conflicting reservation/finalization can be skipped/warned rather than treated as essential build output. This is an immutable-key/archive workflow, not continuous per-operation cache replication: the archive is created before upload. [Official toolkit cache implementation](https://github.com/actions/toolkit/blob/main/packages/cache/src/cache.ts); [Azure upload helper](https://github.com/actions/toolkit/blob/main/packages/cache/src/internal/uploadUtils.ts); [older reserve/upload API](https://github.com/actions/toolkit/blob/main/packages/cache/src/internal/cacheHttpClient.ts).

**Could not verify:** GitHub's private production cache service implements reservation using an Azure blob lease specifically. The open client contains reservation semantics and Azure uploads, but no evidence establishing the private service's lock algorithm. Azure's own Lease Blob API is verified prior art: write/delete leases may be finite (15–60 seconds) or infinite and support acquire/renew/release/break. Do not turn that general primitive into a claim about GitHub's internals. [Azure Lease Blob](https://learn.microsoft.com/en-us/rest/api/storageservices/lease-blob); [official client](https://github.com/actions/toolkit/blob/main/packages/cache/src/cache.ts).

A **public implementation**, `falcondev-oss/github-actions-cache-server`, implements Actions cache API v2 with S3/GCS/Azure/filesystem drivers and persistent database metadata. Its documentation describes reserve/upload/finalize and its code implements **database-backed, expiring merge leases and reader leases**, with ownership tokens and conditional renewal. This is inspectable lease/recovery prior art, not evidence of what GitHub uses internally. [Project](https://github.com/falcondev-oss/github-actions-cache-server); [flow](https://github.com/falcondev-oss/github-actions-cache-server/blob/dev/website/src/content/docs/how-it-works.md); [lease code](https://github.com/falcondev-oss/github-actions-cache-server/blob/dev/src/storage/leases.rs).

### OCI registry as cache

OCI distribution explicitly supports concurrent blob uploads and digest deduplication, including concurrent identical layer uploads, resumable sessions, cancelation, and publishing blobs before manifests. An OCI registry supplies a mature transport/storage boundary; it does **not** give an automatic union of all builders' manifests when they race to update one tag. Use immutable digest/build identifiers or a coordinated alias publisher. [OCI distribution specification](https://github.com/opencontainers/distribution-spec/blob/main/spec.md); [Docker cache location overwrite warning](https://docs.docker.com/build/cache/backends/).

CNCF Distribution has an S3-compatible storage driver and can redirect reads to presigned storage URLs. Its documented mark-and-sweep GC needs uploads stopped/read-only during collection to avoid deleting newly uploaded but not-yet-marked content. That is a real concurrent-reader/writer lifecycle concern, distinct from normal concurrent blob PUT safety. [S3 driver](https://distribution.github.io/distribution/storage-drivers/s3/); [GC constraints](https://distribution.github.io/distribution/about/garbage-collection/).

## 6. S3 semantics and economic consequences

### Correctness primitives

1. **Strong consistency:** successful object writes/overwrites/deletes are immediately reflected by subsequent reads and LIST. A single object's replacement is atomic: readers see old or new, not a torn object. This does not supply a transaction across a blob and an index object. AWS also notes that concurrent write precedence cannot be inferred from client completion order. [S3 consistency](https://aws.amazon.com/s3/consistency/); [detailed consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).
2. **Conditional create:** `If-None-Match: *` can enforce create-if-absent with PutObject and CompleteMultipartUpload. A losing concurrent create normally gets 412; concurrent delete/write situations may give 409, with multipart retries requiring re-initiation in documented cases. `If-Match: <ETag>` supplies compare-and-swap-style protection for mutable metadata. Handle conflict/retry explicitly; HEAD then PUT is not equivalent. [Conditional write documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).
3. **Multipart:** initiate → upload numbered parts → complete; the final object is available after completion. Uploaded parts incur storage charges until completion or abort, and uploads do not expire by themselves. Persist upload-session IDs/part receipts outside disposable nodes if another process must finish them; otherwise abort best-effort and sweep abandoned uploads. An ETag is not necessarily an MD5/content digest, so keep an explicit content hash/checksum. [Multipart lifecycle, concurrency, checksums and billing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html).
4. **Lifecycle/GC:** configure `AbortIncompleteMultipartUpload` separately from ordinary object expiration; use expiration and noncurrent-version policies consciously. **Design inference:** delete/expire action records before referenced blobs, retain blobs with a grace period for active readers/uploads, or use lease/reachability-aware GC; ordinary age-only lifecycle cannot discover cache graph references. Reads alone are not BuildKit's touch mechanism—its exporter uses COPY. [Incomplete upload lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html); [expiration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html); [REAPI retention guidance](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto); [BuildKit touch](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/s3.go).
5. **Compatible does not mean identical:** S3-compatible endpoint support exists in these clients, but AWS consistency/conditional-write/checksum claims apply to AWS S3. Test the chosen MinIO/Ceph/R2/etc. deployment's semantics and proxy behavior; no independent conformance/load testing was performed here. [BuildKit endpoint options](https://github.com/moby/buildkit#s3-cache-experimental); [sccache endpoint support](https://github.com/mozilla/sccache/blob/main/docs/S3.md).

### Explicit request-cost example, not a measured workload

The official AWS regional public pricing JSON was fetched during research. For **S3 Standard, US East (N. Virginia)** it lists **$0.005 per 1,000 PUT/COPY/POST/LIST requests**, **$0.0004 per 1,000 GET/other Tier-2 requests**, and **$0.023/GB-month** for the first storage tier. Other regions/classes and providers differ. [Official machine-readable regional price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/us-east-1/index.json); [pricing explanation](https://aws.amazon.com/s3/pricing/).

Illustrative assumptions: **10,000 CI jobs/day**, **3,000 GET/HEAD requests/job**, **500 Tier-1 requests/job**, **30 days/month**. Python-evaluated calculations:

| Component | Calculation | Cost |
|---|---|---:|
| GET/HEAD | 10,000 × 3,000 × $0.0000004 | $12/day |
| PUT/COPY/POST/LIST | 10,000 × 500 × $0.000005 | $25/day |
| Requests combined | ($12 + $25) × 30 | **$1,110/month** |
| Same pattern at 10× scale | $1,110 × 10 | **$11,100/month** |
| Illustrative 1,000 GB steady storage | 1,000 × $0.023 | $23/month |

These are computed scenarios, **not observed CI counts or a full quote**. They exclude data transfer to on-prem, connectivity/NAT, retries, KMS requests, cache gateway/database compute, lifecycle/version amplification, and incomplete upload storage. The 500 Tier-1 count must include all multipart create/part/complete and COPY-touch requests; it must not be misread as 500 objects regardless of multipart size. Regional pricing and multipart billing sources: [AWS price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/us-east-1/index.json); [S3 pricing](https://aws.amazon.com/s3/pricing/); [multipart billing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html).

**Design implication:** many tiny cache objects can make request cost and latency more important than raw stored GB. Batch metadata queries/missing-blob checks, reuse connections, deduplicate content, and consider packed/chunked artifacts while measuring lost reuse and overfetch. HEAD-before-every-write and periodic COPY touches are measurable extra requests, not free operations. This is an architectural inference, not a benchmark result. [BuildKit HEAD/touch code](https://github.com/moby/buildkit/blob/master/cache/remotecache/s3/s3.go); [REAPI batch/missing-blob APIs](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto); [AWS pricing](https://aws.amazon.com/s3/pricing/).

## 7. Design for nodes that disappear in 30 seconds

The following is a **proposed design synthesized from prior art**, not a claim that stock Dagger currently implements these guarantees.

1. **Keep the durability boundary off the dying node.** Engines/runners may have disposable local read caches, but an acknowledged shared-cache commit must include completed remote blob writes and durable metadata, not merely enqueueing them locally. Keep an asynchronous gateway persistent, or make its acknowledgement explicitly mean remote completion. [Bazel-remote queue behavior](https://github.com/buchgr/bazel-remote/blob/master/README.md); [REAPI retention model](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto).
2. **Upload during normal operation, not only on successful job/session shutdown.** Stream generated artifacts or upload each completed operation/task promptly. Use a bounded queue with visible backlog/oldest-unflushed age; dropping a cache write is acceptable, claiming it is durable is not. Dagger's beta protocol is service-driven and asynchronous, so merely enabling it does not prove this stronger write-through contract. [Dagger export/upload protocol](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/protocol/protocol.go); [cancelation behavior](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/remotecache.go); [streaming upload/abort example](https://github.com/ducktors/turborepo-remote-cache/blob/main/src/plugins/remote-cache/storage/s3.ts).
3. **Commit in order:** unique upload session → hash-checked complete blob(s) → atomically publish the action/task record. Prefer content-addressed immutable blobs and per-action records; use conditional create for deterministic first-writer-wins entries or CAS/version fencing for mutable aliases. A worker dying before metadata publication leaves harmless reclaimable orphan blobs; a published record with missing data must become a miss/recompute, never a fabricated successful build. [OCI publish order/concurrency](https://github.com/opencontainers/distribution-spec/blob/main/spec.md); [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html); [Nx non-overwrite contract](https://nx.dev/docs/guides/tasks--caching/self-hosted-caching).
4. **Do not hold global locks for transfers.** At most coordinate each key/upload using finite leases and ownership/fencing tokens, with renewals and takeover after expiry. Prefer redundant immutable uploads over a global shared index lock; serialize only publication where required. Expired owners must not publish over a replacement. These are design choices illustrated by REAPI upload identities and the public Actions-compatible server's expiring leases. [REAPI](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto); [lease implementation](https://github.com/falcondev-oss/github-actions-cache-server/blob/dev/src/storage/leases.rs); [Azure lease primitive](https://learn.microsoft.com/en-us/rest/api/storageservices/lease-blob).
5. **Bound failure cost and fail safely.** On cache outage, run the actual task; use short cache lookup/upload budgets and explicit best-effort export policy where the tool supports it. Treat invalid signatures/digests and missing referenced bytes as misses, while emitting corruption/error metrics; do not conceal a real task failure as a cache miss. Cache policy is not universal across tools—BuildKit's exporter defaults to error-sensitive unless `ignore-error=true`, whereas Turbo documents failed signature verification as a miss. [BuildKit options](https://github.com/moby/buildkit#s3-cache-experimental); [Turbo verification](https://turborepo.com/docs/core-concepts/remote-caching).
6. **Shutdown is only an optimization.** Stop accepting new work, try flushing the already-small backlog, cancel/abort unfinished transfers, and exit before the platform kills the pod. Previously committed objects remain reusable. A 1 GiB backlog needs about **34.13 MiB/s** just to transmit within 30 seconds, before hashing, retries and commit overhead (Python: 1024/30). No shutdown hook can save bytes a task has not produced or a network cannot transmit. [Multipart completion/abort semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html); [Dagger upload cancelation](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/engine/remotecache/remotecache.go).
7. **Protect both trust and lifecycle boundaries.** Namespace by tenant/repo/platform/toolchain/key version; give untrusted PRs read-only credentials or separate write scopes; use TLS, restricted bucket/presign permissions, and artifact verification. Run multipart cleanup and conservative blob GC outside the disposable worker. Hashes alone authenticate content, not who was allowed to claim that content is the result of a particular action. [Bazel trusted-writer guidance](https://bazel.build/remote/caching); [Turbo HMAC](https://turborepo.com/docs/core-concepts/remote-caching); [Actions-compatible repository scoping](https://github.com/falcondev-oss/github-actions-cache-server/blob/dev/website/src/content/docs/how-it-works.md); [S3 cleanup](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html).

### Dagger-specific termination warning

A reported Dagger-main local-persistence issue shows clean shutdowns taking 49 seconds to several minutes, and interrupted closes causing the entire dagql/local worker cache to be discarded on next startup. PR #15052 proposes detaching the final persist from the graceful-stop budget, but was **open/unmerged** when checked and explicitly does not solve SIGKILL. This evidence is from the reported main build, **not a tested reproduction on this cluster's v0.21.9**. It is nevertheless enough to reject an unverified assumption that “a PVC plus 30 seconds always preserves Dagger cache.” [Issue #14956 with measurements](https://github.com/dagger/dagger/issues/14956); [proposal/scope #15052](https://github.com/dagger/dagger/pull/15052).

### Recommended next decision for this deployment

**Near term:** keep Dagger engines on non-preemptible/persistent nodes (or persistent engine hosts), keep ARC runners disposable, and evaluate sccache/Bazel/Turbo/Nx caches for workloads they actually cover. **If disposable engines are mandatory:** treat a beta-compatible Dagger cache server as a new engineering project, including telemetry ingestion, protocol/version pinning, durable metadata and S3 uploads, reconnection/reconciliation, leases/GC, tenant isolation, and failure injection. Do not present the obsolete environment variable, a Magicache Helm switch, or a bare S3 bucket as a finished solution. [Official persistent-engine recommendation](https://docs.dagger.io/self-hosting/index); [removal confirmation](https://github.com/dagger/dagger/issues/13405); [new protocol boundaries](https://github.com/dagger/dagger/pull/14388); [separate cache-event exporter](https://github.com/dagger/dagger/blob/v1.0.0-beta.25/cmd/engine/telemetry.go).
